# Java Link DB導入検討

## 1. 目的

現在のJava Linkでは、学習中の進捗をHTTPセッションで管理している。

ページの再読み込みやJava Linkトップ画面への移動後も学習状態は保持されるが、
利用終了後も継続して学習進捗を保存する仕組みは持っていない。

Java Linkを継続的に利用できる学習Webアプリとして発展させるため、
学習進捗をデータベースへ永続化し、
次回の利用時に前回の続きから学習を再開できる仕組みを検討する。

また将来的には、過去の学習状況を記録し、
利用者がこれまでの学習履歴を確認できる機能への発展も検討する。


## 2. 現状調査

### 2.1 学習進捗の管理方法

現在のJava Linkでは、`LessonProgressService` が `HttpSession` を利用して、
教材ごとの学習進捗を管理している。

`LessonProgressService` には、主に次の処理がある。

- `getProgress()`：指定した教材の学習進捗をセッションから取得する
- `saveProgress()`：指定した教材の学習進捗をセッションへ保存する

教材ごとの進捗は、`lessonId` と `LessonProgress` を対応させたMapとして管理されている。


### 2.2 現在保持している学習状態

`LessonProgress` は、1つの教材に対する学習進捗を表すクラスであり、
教材そのもののデータとは分離して、学習によって変化する状態を保持している。

現在は次の情報を保持している。

- `lessonId`
- `currentStepId`
- `completedStepIds`
- `selectedOptionId`
- `answered`
- `correct`
- `completed`
- `programExecuted`

これらの情報をすべてDBへ保存するとは限らない。

今後、
「セッション中だけ必要な状態」と
「次回利用時にも復元する必要がある状態」
を整理したうえで、DBへ永続化する情報を決定する。


## 3. DBへ保存する学習状態

### 3.1 復元する範囲

第一段階では、
次回の利用時に前回学習していた教材とStepを復元し、
そのStepから学習を再開できるようにする。

Java Linkでは現在、コード要素ごとの確認状態を
`completedStepIds` で管理し、💡の点灯状態として画面に反映している。

ただし第一段階のDB永続化では、
コード要素ごとの確認状態や💡個別の点灯状態までは保存せず、
現在の学習位置を表すStep単位で進捗を保存する。

これにより、
DB設計を必要以上に複雑にせず、
「前回の続きから学習を再開する」という
第一段階の目的を優先する。

コード要素ごとの確認状態や💡の点灯状態の永続化については、
必要に応じて将来の拡張として検討する。


### 3.2 現在の状態との対応

現在の `LessonProgress` には、
学習位置を管理する情報として `currentStepId` が保持されている。

第一段階では、
このStep単位の学習位置をDBへ保存し、
次回利用時の再開位置として利用する。

`completedStepIds` は現在の学習中の状態管理には引き続き利用するが、
第一段階ではDBへの保存対象には含めない。

また、
現在 `LessonProgress` が保持しているすべての情報を、
そのままDBへ保存するわけではない。

HTTPセッションで管理する一時的な状態と、
利用終了後も保持する必要がある状態を分けて管理する。


## 4. 永続化する情報の検討

現在の `LessonProgress` が保持している情報について、
第一段階でDBへ保存する状態かどうかを整理する。

| 項目 | DB保存 | 理由 |
| --- | --- | --- |
| `lessonId` | ○ | どの教材の学習進捗なのかを識別するために必要 |
| `currentStepId` | ○ | 次回利用時に前回のStepから学習を再開するために必要 |
| `completedStepIds` | × | 第一段階ではコード要素ごとの確認状態や💡個別の点灯状態までは復元しない |
| `selectedOptionId` | × | 選択中の回答は利用中だけ必要な一時的な状態として扱う |
| `answered` | × | 回答済みという画面状態は利用中だけ必要な一時的な状態として扱う |
| `correct` | × | 直前の回答結果は利用中だけ必要な一時的な状態として扱う |
| `completed` | ○ | 教材を完了しているかを判定するために必要 |
| `programExecuted` | × | プログラム実行済みという画面状態は利用中だけ必要な一時的な状態として扱う |

第一段階では、
前回の学習位置から再開するために必要な情報に絞って永続化する。

`completedStepIds` については、
現在の学習中の状態管理には引き続き利用するが、
第一段階ではDBへの保存対象には含めない。

コード要素ごとの確認状態や💡個別の点灯状態を
次回利用時にも復元する必要が生じた場合には、
将来の拡張として保存方法を改めて検討する。

実際のDB設計では、
現在のJavaクラスのフィールドをそのままDBの列へ対応させるのではなく、
利用者を識別する情報や更新日時なども含めて、
永続化に必要なデータ構造を設計する。


## 5. 利用者の識別

学習進捗を利用終了後も保存するためには、
「誰の学習進捗なのか」を識別する必要がある。

現在はHTTPセッション単位で学習状態を管理しているため、
永続的に利用者を識別する仕組みは持っていない。

DB導入にあわせてログイン機能を追加し、
ログインした利用者と学習進捗を関連付ける。


### 5.1 ログイン方式

Java Linkの認証には、Spring Securityを使用する。

第一段階では、
メールアドレスとパスワードによるログイン方式を採用する。

新規登録時には、利用者が次の情報を入力する。

- 表示名
- メールアドレス
- パスワード

Googleアカウントなどを利用した外部サービスとのログイン連携や、
多要素認証については第一段階の実装範囲には含めない。


### 5.2 利用者データ

第一段階では、利用者について次の情報を保存する。

| 項目 | 用途 |
| --- | --- |
| `id` | 利用者を一意に識別する内部ID |
| `display_name` | Java Link上で表示する名前 |
| `email` | ログインに使用するメールアドレス |
| `password_hash` | PasswordEncoderで変換したパスワードの値 |
| `created_at` | アカウントの登録日時 |

`id` は利用者自身が入力する情報ではなく、
Java Link内部で利用者を識別するために使用する。

Java側では `Long` 型とし、
新規登録時に自動生成する構成とする。

`email` はログイン時の利用者識別に使用するため、
重複を許可しない。

`display_name` は画面表示用の情報であるため、
他の利用者との重複を許可する。

利用者が入力したパスワードは平文のままDBへ保存せず、
Spring SecurityのPasswordEncoderを利用して変換した値を保存する。

アカウント情報の更新日時を表す `updated_at` については、
第一段階ではアカウント編集機能を実装しないため保存対象に含めず、
アカウント編集機能を追加する際に導入を検討する。


### 5.3 学習進捗との関連

学習進捗には利用者の内部IDを関連付け、
どの利用者の学習進捗なのかを識別できるようにする。

第一段階では、
1人の利用者について、教材ごとに1つの学習進捗を管理する。

概念的には、次の関係となる。

```text
利用者
  ↓
教材ごとの学習進捗
  ↓
現在のStep・教材の完了状態
```

これにより、
ログインした利用者に対応する教材ごとの学習進捗をDBから取得し、
前回のStepから学習を再開できる構成とする。


### 5.4 教材データとの関連

第一段階では、教材そのもののデータはDBへ保存せず、
現在と同様にJava側で管理する。

学習進捗には、Java側の教材を識別するための `lesson_id` を保存する。

`lesson_id` はDB上の教材テーブルを参照する外部キーとはせず、
Java側で管理している教材の識別子と対応させる。

これにより第一段階では、
教材データのDB化まで実装範囲を広げず、
利用者ごとの学習進捗の永続化を優先する。

教材そのものをDBで管理する必要が生じた場合には、
将来の拡張として教材テーブルの導入を検討する。


## 6. セッションとDBの役割

DB導入後も、
HTTPセッションを完全に廃止するとは限らない。

それぞれの役割を次のように分けることを検討する。


### HTTPセッション

現在利用している画面や、
一時的な回答状態など、
利用中だけ必要な状態を保持する。


### データベース

利用終了後も保持する必要がある学習進捗を保存する。

これにより、
「現在の利用中の状態」と
「次回利用時にも必要な状態」
を分けて管理する。


## 7. 学習履歴

第一段階では、
「前回の続きから学習を再開するための現在の進捗」
の永続化を優先する。

将来的には現在の進捗とは別に、
過去の学習履歴を記録する機能も検討する。

例：

- Stageの完了記録
- Stageの完了日時
- 最終学習日時
- 学習したStageの一覧

現在状態と履歴では目的が異なるため、
DB設計時には別のデータとして管理することを検討する。


## 8. DB・永続化技術の選定

Java Linkの学習進捗を永続化するため、
使用するDBとJavaからDBを利用する方法について検討した。


### 8.1 DB

DBには、PostgreSQLを採用する。

Java Linkでは今後、

- 利用者ごとの学習進捗
- ログイン機能
- 学習履歴

などを扱うことを想定している。

そのため、学習・開発用途だけではなく、
継続的に利用するWebアプリのデータを管理できる
リレーショナルデータベースとしてPostgreSQLを採用する。

H2 Databaseについては、
必要に応じて開発・テスト用途で利用する可能性はあるが、
Java Linkの学習進捗を永続化するDBとしてはPostgreSQLを使用する。


### 8.2 JavaからDBを利用する方法

Java LinkからPostgreSQLへアクセスする方法には、
Spring Data JPAを採用する。

Java LinkはSpring Bootを使用しているため、
Spring Data JPAを利用し、
Repositoryを通じてデータアクセス処理を管理する構成とする。

これにより、

- 学習進捗の保存
- 学習進捗の取得
- 利用者と進捗データの関連付け

などのデータアクセス処理を、
Serviceの処理と分離して管理する。

JDBCを利用してSQLやDAOを直接実装する方法もあるが、
Java LinkではSpring Bootの構成との相性や、
今後の機能拡張を考慮してSpring Data JPAを採用する。


### 8.3 採用する構成

現時点では、DB・永続化技術について次の構成を採用する。

```text
Java Link
   ↓
Spring Data JPA
   ↓
PostgreSQL
```


## 9. 第一段階の実装範囲

DB導入の第一段階では、
機能を広げすぎず、次の実現を目標とする。

「利用者ごとの学習進捗を保存し、
次回の利用時に前回の続きから学習を再開できる」

第一段階では、
利用者ごと・教材ごとに現在のStepと教材の完了状態を保存し、
次回ログイン時に前回のStepから学習を再開できるようにする。

確認済みコード要素や💡個別の点灯状態については、
第一段階ではDBへの保存・復元の対象には含めない。

学習履歴一覧などの追加機能については、
進捗の永続化が完成した後に検討する。


## 10. 今後の検討事項

### 決定済み

- DB製品：PostgreSQL
- 永続化技術：Spring Data JPA
- 認証：Spring Security
- ログイン方式：メールアドレスとパスワードによるログイン
- 新規登録情報：表示名・メールアドレス・パスワード
- 利用者データ：`id`、`display_name`、`email`、`password_hash`、`created_at`
- 利用者の内部ID：`Long` 型で新規登録時に自動生成
- パスワード：PasswordEncoderで変換した値をDBへ保存
- 学習進捗：利用者の内部IDと関連付ける
- 学習進捗：1人の利用者について、教材ごとに1つの進捗を管理する
- 第一段階では現在のStepと教材の完了状態をDBへ保存する
- `completedStepIds` は第一段階ではDBへ保存しない
- 確認済みコード要素や💡個別の点灯状態は第一段階では復元対象に含めない
- 教材そのものは第一段階ではDBへ保存せず、Java側で管理する
- 学習進捗の `lesson_id` はJava側の教材識別子と対応させる

### 今後検討する事項

- 学習進捗データの具体的なDBデータ型・制約
- HTTPセッションとDBの責務分担
- DBへの保存タイミング
- DBからの復元タイミング
- 「最初からやり直す」実行時のDB上の進捗の扱い
- 学習履歴のデータ設計
- 既存テストへの影響
- DBを利用したテストの追加


## 11. 第一段階のDB設計ドラフト

第一段階では、利用者情報と教材ごとの学習進捗を保存するため、
次の2つのテーブルを作成することを想定する。

- `users`
- `learning_progress`

本章の内容は実装前のドラフトとし、
Spring Data JPAによるEntity設計や実装を進める際に、
必要に応じて型・制約・保存方法などを確認して調整する。


### 11.1 users テーブル

Java Linkを利用する利用者のアカウント情報を保存する。

| 項目 | 用途 |
| --- | --- |
| `id` | 利用者を一意に識別する内部ID |
| `display_name` | Java Link上で表示する名前 |
| `email` | ログインに使用するメールアドレス |
| `password_hash` | PasswordEncoderで変換したパスワードの値 |
| `created_at` | アカウントの登録日時 |

`id` は主キーとし、Java側では `Long` 型として扱う。
新規登録時に自動生成する。

`email` はログイン時の利用者識別に使用するため、
重複を許可しない。

`display_name` は画面表示用の情報であるため、
他の利用者との重複を許可する。

パスワードは平文では保存せず、
Spring SecurityのPasswordEncoderで変換した値を
`password_hash` に保存する。


### 11.2 learning_progress テーブル

利用者ごとの教材の学習進捗を保存する。

| 項目 | 用途 |
| --- | --- |
| `id` | 学習進捗を一意に識別する内部ID |
| `user_id` | どの利用者の学習進捗かを識別する |
| `lesson_id` | Java側で管理している教材を識別する |
| `current_step_id` | 次回利用時に再開するStepを表す |
| `completed` | 教材を完了しているかを表す |
| `updated_at` | 学習進捗を最後に更新した日時 |

`id` は主キーとし、Java側では `Long` 型として扱う。
新しい学習進捗を作成するときに自動生成する。

`user_id` は `users` テーブルの `id` と関連付け、
どの利用者の学習進捗なのかを識別する。

`lesson_id` には、
Java側で管理している教材の識別子を保存する。

第一段階では教材そのものをDBへ保存しないため、
`lesson_id` は教材テーブルへの外部キーとはしない。

`current_step_id` には、
次回利用時に学習を再開するStepの識別子を保存する。

`completed` には、
その教材を完了しているかどうかを保存する。

`updated_at` には、
学習進捗を最後に更新した日時を保存する。


### 11.3 利用者と学習進捗の関係

1人の利用者は、
複数の教材について学習進捗を持つことができる。

概念的には次の関係となる。

```text
users
  │
  ├── learning_progress（lesson-1）
  ├── learning_progress（lesson-2）
  └── learning_progress（lesson-3）
```

`learning_progress.user_id` を
`users.id` と関連付けることで、
学習進捗がどの利用者のものなのかを識別する。

また、同じ利用者について同じ教材の学習進捗が
複数作成されないように、
`user_id` と `lesson_id` の組み合わせを一意とする。


### 11.4 第一段階では保存しない情報

現在の `LessonProgress` が保持している情報のうち、

- `completedStepIds`
- `selectedOptionId`
- `answered`
- `correct`
- `programExecuted`

については、第一段階ではDBへ保存しない。

これらは現在の利用中に必要となる一時的な状態として扱い、
必要に応じてHTTPセッションで管理する。

コード要素ごとの確認状態や💡個別の点灯状態を
次回利用時にも復元する必要が生じた場合には、
将来の拡張としてDBへの保存方法を検討する。


### 11.5 現時点のテーブル構成

```text
users
────────────────────
id
display_name
email
password_hash
created_at


learning_progress
────────────────────
id
user_id
lesson_id
current_step_id
completed
updated_at
```

テーブル間の関係は次のようになる。

```text
users
────────────────────
id
  │
  │
  └───────────────┐
                  │
                  ▼
learning_progress
────────────────────
id
user_id
lesson_id
current_step_id
completed
updated_at
```

第一段階ではこの構成を基準として実装を進める。

具体的なDBのデータ型、NULLの可否、
Spring Data JPAのEntityとの対応、
外部キーや一意制約の設定方法については、
実装時に確認しながら決定する。
