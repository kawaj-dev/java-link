# Java Link DB導入検討

## 1. 目的

現在のJava Linkでは、学習中の進捗をHTTPセッションで管理している。

ページの再読み込みやJava Linkトップ画面への移動後も学習状態は保持されるが、
利用終了後も継続して学習進捗を保存する仕組みは持っていない。

Java Linkを継続的に利用できる学習Webアプリとして発展させるため、
学習進捗をデータベースへ永続化し、
次回の利用時に前回の続きから学習を再開できる仕組みを検討する。

また将来的には、過去の学習状況を記録し、
利用者がこれまでの学習履歴を確認できる機能への発展も検討する。

## 2. 現状調査

### 2.1 学習進捗の管理方法

現在のJava Linkでは、`LessonProgressService` が `HttpSession` を利用して、
教材ごとの学習進捗を管理している。

`LessonProgressService` には、主に次の処理がある。

- `getProgress()`：指定した教材の学習進捗をセッションから取得する
- `saveProgress()`：指定した教材の学習進捗をセッションへ保存する

教材ごとの進捗は、`lessonId` と `LessonProgress` を対応させたMapとして管理されている。


### 2.2 現在保持している学習状態

`LessonProgress` は、1つの教材に対する学習進捗を表すクラスであり、
教材そのもののデータとは分離して、学習によって変化する状態を保持している。

現在は次の情報を保持している。

- `lessonId`
- `currentStepId`
- `completedStepIds`
- `selectedOptionId`
- `answered`
- `correct`
- `completed`
- `programExecuted`

これらの情報をすべてDBへ保存するとは限らない。

今後、
「セッション中だけ必要な状態」と
「次回利用時にも復元する必要がある状態」
を整理したうえで、DBへ永続化する情報を決定する。

## 3. DBへ保存する学習状態

### 3.1 復元する範囲

次回の利用時には、
前回学習していたStage・Partだけでなく、
そのPart内で確認済みだったコード要素の状態まで復元する。

たとえば、Part内で複数のコード要素のうち一部まで確認して学習を終了した場合、
次回の利用時には確認済みのコード要素と💡の点灯状態を復元し、
前回の続きから学習できるようにする。

Java Linkでは、
コード要素を一つずつ確認し、💡が順につながっていくこと自体が学習進捗を表すため、
Part単位だけではなく、コード要素単位まで学習状態を保持する。


### 3.2 現在の状態との対応

現在の `LessonProgress` には、
コード要素単位の学習状態を管理するための情報として、
`currentStepId` や `completedStepIds` などが保持されている。

DB導入時には、
これらの現在の状態管理を確認しながら、
次回利用時の復元に必要な情報を選定する。

現在 `LessonProgress` が保持しているすべての情報を、
そのままDBへ保存するとは限らない。

## 4. 永続化する情報の検討

現在の `LessonProgress` が保持している情報について、
次回利用時にも必要な状態かどうかを整理する。

| 項目 | DB保存候補 | 理由 |
| --- | --- | --- |
| `lessonId` | ○ | どの教材の学習進捗なのかを識別するために必要 |
| `currentStepId` | ○ | どのコード要素まで進んでいたかを復元するために必要 |
| `completedStepIds` | ○ | 確認済みコード要素と💡の点灯状態を復元するために必要 |
| `selectedOptionId` | 要検討 | 選択中の回答まで次回利用時に復元する必要性を検討する |
| `answered` | 要検討 | 回答済みという画面状態まで復元する必要性を検討する |
| `correct` | 要検討 | 直前の回答結果まで復元する必要性を検討する |
| `completed` | ○ | 教材を完了しているかを判定するために必要 |
| `programExecuted` | 要検討 | プログラム実行済みの状態まで復元する必要性を検討する |

第一段階では、
学習位置と確認済みコード要素を復元するために必要な情報を中心に
永続化することを検討する。

現時点での主な候補は次のとおり。

- 教材を識別する情報
- 現在の学習位置を表す情報
- 確認済みコード要素を表す情報
- 教材の完了状態

実際のDB設計時には、
現在のJavaクラスのフィールドをそのままDBの列へ対応させるのではなく、
必要なデータ構造を改めて設計する。


## 5. 利用者の識別

学習進捗を利用終了後も保存する場合、
「誰の学習進捗なのか」を識別する必要がある。

現在はHTTPセッション単位で学習状態を管理しているため、
永続的な利用者識別の仕組みは持っていない。

将来的にはログイン機能を導入し、
利用者と学習進捗を関連付けることを検討する。

概念的には、次の関係となる。

利用者
↓
教材ごとの学習進捗
↓
現在の学習位置・確認済みコード要素・完了状態

ログイン機能の具体的な認証方式については、
DB設計とは分けて検討する。


## 6. セッションとDBの役割

DB導入後も、
HTTPセッションを完全に廃止するとは限らない。

それぞれの役割を次のように分けることを検討する。

### HTTPセッション

現在利用している画面や、
一時的な回答状態など、
利用中だけ必要な状態を保持する。

### データベース

利用終了後も保持する必要がある学習進捗を保存する。

これにより、

「現在の利用中の状態」

と

「次回利用時にも必要な状態」

を分けて管理する。


## 7. 学習履歴

第一段階では、
「前回の続きから学習を再開するための現在の進捗」
の永続化を優先する。

将来的には現在の進捗とは別に、
過去の学習履歴を記録する機能も検討する。

例：

- Stageの完了記録
- Stageの完了日時
- 最終学習日時
- 学習したStageの一覧

現在状態と履歴では目的が異なるため、
DB設計時には別のデータとして管理することを検討する。


## 8. DB・永続化技術の選定

Java Linkの学習進捗を永続化するため、
使用するDBとJavaからDBを利用する方法について検討した。

### 8.1 DB

DBには、PostgreSQLを採用する。

Java Linkでは今後、

- 利用者ごとの学習進捗
- ログイン機能
- 学習履歴

などを扱うことを想定している。

そのため、学習・開発用途だけではなく、
継続的に利用するWebアプリのデータを管理できる
リレーショナルデータベースとしてPostgreSQLを採用する。

H2 Databaseについては、
必要に応じて開発・テスト用途で利用する可能性はあるが、
Java Linkの学習進捗を永続化するDBとしてはPostgreSQLを使用する。

### 8.2 JavaからDBを利用する方法

Java LinkからPostgreSQLへアクセスする方法には、
Spring Data JPAを採用する。

Java LinkはSpring Bootを使用しているため、
Spring Data JPAを利用し、
Repositoryを通じてデータアクセス処理を管理する構成とする。

これにより、

- 学習進捗の保存
- 学習進捗の取得
- 利用者と進捗データの関連付け

などのデータアクセス処理を、
Serviceの処理と分離して管理する。

JDBCを利用してSQLやDAOを直接実装する方法もあるが、
Java LinkではSpring Bootの構成との相性や、
今後の機能拡張を考慮してSpring Data JPAを採用する。

### 8.3 採用する構成

現時点では、DB・永続化技術について次の構成を採用する。

```text
Java Link
   ↓
Spring Data JPA
   ↓
PostgreSQL
```

## 9. 第一段階の実装範囲

DB導入の第一段階では、
機能を広げすぎず、次の実現を目標とする。

「利用者ごとの学習進捗を保存し、
次回の利用時に前回の続きから学習を再開できる」

復元対象には、
前回学習していた位置だけでなく、
確認済みコード要素と💡の点灯状態を含める。

学習履歴一覧などの追加機能については、
進捗の永続化が完成した後に検討する。


## 10. 今後の検討事項

### 決定済み

- DB製品：PostgreSQL
- 永続化技術：Spring Data JPA

### 今後検討する事項

- ログイン機能の方式
- 利用者データの設計
- 学習進捗データのテーブル設計
- `completedStepIds` の保存方法
- HTTPセッションとDBの責務分担
- DBへの保存タイミング
- DBからの復元タイミング
- 「最初からやり直す」実行時のDB上の進捗の扱い
- 学習履歴のデータ設計
- 既存テストへの影響
- DBを利用したテストの追加
